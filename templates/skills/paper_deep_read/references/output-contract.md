# Output Contract

Write three JSON artifacts:

- `source_map.json`
- `note_plan.json`
- `deep_read.json`

Use the evidence-harvest -> interpretation-draft -> schema-write -> self-review gate workflow. Do not fill schemas first: harvest evidence before drafting interpretations, draft paper-specific interpretations before shaping them into schema fields, and the self-review gate must pass before validation.

`math_index.json` is generated by parsing. `formula_vision.json` is generated only by `paper_engine read <bibkey> --vision-formulas` when visual formula fallback is needed. Do not hand-write either file during normal reading.

## `source_map.json`

Use `schemas/source_map.schema.json`. It must include only evidence blocks actually used by the deep-reading report.

Every block must include `section_id`, `paragraph_ids`, and `source_kind`. Body text and caption evidence must point to paragraph IDs from `paper_index.json`.
Math/vision formula evidence may include `image_path`, `latex`, `bbox`, and `backend`. Use `source_kind: "equation"` and an `M###` block ID when a formula comes from `math_index.json` text candidates or `formula_vision.json` image transcription.

External availability evidence uses `E###` block IDs and `source_kind: "external"`. Put the opened source title, URL, access date, and search query or lookup path in `notes`, because the source-map schema does not have dedicated URL/query fields.
If availability mentions a URL, says that an external lookup/search/check was performed, or says that an external lookup/search/check was blocked/unavailable, the relevant `availability.code/data/models.source_refs` must cite an `E###` source block. That block uses `page: 0`, `section_id: "external_availability"`, `source_kind: "external"`, and notes containing `URL: ...; accessed: YYYY-MM-DD; query or lookup: ...`. If no external lookup was performed and no URL is claimed, do not mention external lookup/search/check in availability prose.

## `note_plan.json`

Write this before `deep_read.json`. Required fields:

- `schema_version`
- `primary_type`
- `active_lenses`
- `type_rationale`
- `must_cover`
- `key_numbers`
- `central_claims`
- `claim_boundaries`
- `mechanism_result_map`
- `comparative_positioning`
- `negative_or_limiting_results`
- `visual_plan`
- `section_plan`

`primary_type` is exclusive. `active_lenses` is multi-label and must include `primary_type`.

## `deep_read.json`

Use `schemas/deep_read_report.schema.json`.

Required top-level sections:

- `paper_profile`
- `argument_map`
- `quick_read`
- `central_claims`
- `method_understanding`
- any type-specific understanding sections required by active lenses
- `evaluation`
- `visual_cards`
- `availability`
- `extraction_notes`
- `translations`

`translations.zh` must translate reader-facing conclusions into Chinese. Translate summaries, quick-read items, argument-map text, central claims, method/evaluation text, visual-card labels/captions/notes, availability evidence/notes, type-specific sections, and extraction notes. Do not translate paths, BibTeX keys, DOI/arXiv IDs, URLs, numbers, equations, or `source_refs`.

Chinese coverage is part of the output contract, not a cosmetic afterthought. Before validation, compare the English reader-facing fields against `translations.zh`: every displayed explanatory sentence needs a Chinese counterpart, and copied English text is not acceptable as a fallback. Short technical labels may remain bilingual or English when that is the natural term, but paragraphs, claims, evidence summaries, limitations, result interpretations, visual-card notes, and extraction notes must be Chinese. The validator rejects missing or copied-English reader text; Markdown and HTML should not rely on English fallback for Chinese mode.

For structured sections, the Chinese mirror must preserve the same list/object shape for displayed subfields. In particular, translate every `method_understanding.algorithm_steps[].action/inputs/outputs`, every `evaluation.numeric_results[].dataset_or_task/metric/interpretation/what_it_does_not_prove`, every `theory_understanding.key_equations[].label/explanation`, every `theory_understanding.theorem_or_principle_chain[].principle/role/intuition`, and every `survey_understanding.method_family_matrix[].family/core_idea/strengths/limitations/best_for`. Do not replace these with one paragraph summary.

For `dataset_benchmark_understanding.format: "structured_v2"`, preserve row order and translate every `key_numbers[].label/context` and every `construction_steps[].stage/action/output/quality_control`. Do not duplicate language-neutral `value`, `unit`, or `source_refs` inside the Chinese mirror; the renderer reuses them from the source rows. Dataset key numbers describe the corpus itself; model metrics and solver performance belong in `evaluation.numeric_results`.

Interpretation quality is also part of the output contract. Reader-facing prose must synthesize what the evidence means, not paste source blocks into templates. An adjacent-domain reader should understand the paper's concrete problem, method, mechanism, equations or variables, experiment setup, main evidence, and limits without opening the PDF. Every quick-read item must name a concrete method, theorem, example, equation family, dataset, solver, benchmark, code artifact, or limitation from this paper. Availability evidence must interpret the external or paper-local availability check; it must not copy the `E###.source_text` string or HTTP/search result verbatim. Avoid generic wrappers such as "the paper frames its contribution around", "the motivating problem is", "the main evidence is", "concrete intervention or analysis route", "tasks, baselines, or benchmarks", "reported evidence", "studies an optimal-control method or theory component", "the key evidence is that", and generic Chinese placeholders such as "结合英文证据/source_refs 理解", "以原文为准", repeated "该论文从某方向出发", "这张卡片说明文献如何处理最优控制中的建模、求解或理论分析", or "文献给出一种围绕最优控制建模与求解的结构化说明". If the report cannot say something paper-specific, leave the field empty only when the schema allows it or state the specific extraction limitation in `extraction_notes`.
Do not copy `source_map.blocks[].source_text` into reader-facing fields. Source blocks are citations; reader-facing fields must be interpretation. In particular, `argument_map.decisive_evidence[].text` should explain why the cited evidence matters rather than repeat the cited sentence.

Reader-facing Markdown, HTML, and `deep_read.json` prose must not mention prompt instructions, reading-plan steps, validator requirements, quality-audit wording, schema instructions, parser workflow, validation retries, or the fact that the job is a reread. `note_plan.json` is internal planning evidence, not reader-facing content; validation and quality-audit errors are repair instructions, not content to summarize. Never write user-facing phrases such as "this reread", "the reread", "selected evidence", "evidence block", "reading bundle", "本次重读", "所选证据", or "证据块".

`method_understanding` must include `pipeline`, `algorithm_steps`, `engineering_derivation_sketch`, and `implementation_details` when those components exist in the paper. `algorithm_pseudocode` may be included as a compact text fallback, but any non-empty pseudocode must also have structured `algorithm_steps` with short readable actions, inputs, outputs, and `source_refs`. Leave both empty only when the paper has no algorithmic procedure to reconstruct.
If `algorithm_pseudocode` is longer than one short sentence, format it as multiple lines with newline characters. A long single-line numbered list is rejected because it renders poorly in HTML.

When `theory` is active, `theory_understanding` must include `problem_formulation`, `key_equations`, and `theorem_or_principle_chain` when the paper contains them. If parsed formulas are degraded, use `math_index.json` text candidates first, then run `paper_engine read <bibkey> --vision-formulas` and use `formula_vision.json` for page-image formula evidence. Only leave `extraction_notes.low_confidence_equations` without key equations when `math_index.json` records that vision fallback was blocked, exhausted, or completed with no visible formulas.

When `survey` is active, `survey_understanding` must include a `method_family_matrix` comparing method families and `timeline_milestones` when the paper provides historical or method-evolution cues. Each method-family row must be evidence-backed enough to state a concrete mechanism, strength, limitation, and best use case. Do not add a matrix row whose content is essentially "the paper mentions this but evidence is insufficient"; put that in `coverage_gaps` or `extraction_notes.missing_sections` instead. If no timeline exists in the paper, record that in `extraction_notes.missing_sections`.

If a lens is active, include its section:

- `method` -> `method_understanding`
- `theory` -> `theory_understanding`
- `dataset_benchmark` -> `dataset_benchmark_understanding`
- `survey` -> `survey_understanding`
- `application` -> `application_understanding`
- `system_tooling` -> `system_understanding`

For a new `dataset_benchmark` report, the section must use `format: "structured_v2"`, a concise evidence-backed `key_numbers` table, and an ordered `construction_steps` pipeline. Do not emit the legacy `data_construction`/`statistics` list shape for new reads. Existing legacy reports remain readable for compatibility only.

Every claim, result, quick-read item, argument-map item, and visual card must cite `source_refs` that exist in `source_map.json`.

Do not include the reading plan itself in reader-facing Markdown or HTML. `note_plan.json` is an internal planning and validation artifact.

For `availability.code`, `availability.data`, and `availability.models`, do not rely only on paper text. Each item must incorporate the limited external availability search from the skill and cite at least one local source ref or one `E###` external source block in `source_refs` whenever it states an availability status, URL, evidence sentence, or note. If external search is blocked or unavailable, record the blocker in the relevant availability `notes` and in `extraction_notes.external_info_used`; do not invent code, data, or model links.

## Source Policy

Ground findings in local artifacts first: metadata, parsed text, visual index, page images, and PDF. If external information is used, label it in `extraction_notes.external_info_used`.

Do not invent code links, data links, citation facts, benchmark numbers, or author affiliations.

For multi-paper or all-library rereading jobs, use `paper_engine read-many` from `skills/paper_reread/SKILL.md`. It runs one independent paper job per bibkey, with a persistent reader session and an independent reviewer session for that paper. The controller, not the main Codex session, copies accepted staged artifacts into `papers/<bibkey>/` after reviewer approval, per-paper validation, note rebuild, quality audit, and selected repeated-text audit. Treat repeated reader-facing text across the selected papers as a quality failure, even when each paper passed single-paper validation. For all-library jobs, run `paper_engine tool audit-readings --json` after `read-many` completes if a full-library check is needed.
