# paper_deep_read

Use the current Codex session to read one paper and write traceable deep-reading artifacts. Do not call arbitrary `codex exec` or spawn another model process from this skill. The model-backed exceptions are project CLI commands with bounded artifact contracts: `battery_lit read <bibkey> --vision-formulas` for selected formula pages, and, for multi-paper jobs routed through `paper_reread`, `battery_lit read-many` for controlled independent reader/reviewer paper jobs.

Read one paper at a time. Do not scan every paper directory or read every `deep_read.json`. For multi-paper or all-library rereads, use `skills/paper_reread/SKILL.md` and its `battery_lit read-many` workflow; do not manually loop over papers and write final artifacts directly. Never replace reading work with a deterministic draft writer, helper script, parsed/index-only bulk generator, or schema filler.

## Inputs

- `papers/<bibkey>/metadata.yml`
- `papers/<bibkey>/paper_index.json`
- `papers/<bibkey>/math_index.json`
- `papers/<bibkey>/formula_vision.json` when `math_index.json` required visual formula fallback
- `papers/<bibkey>/parsed.md`
- `papers/<bibkey>/visual_index.md` and `papers/<bibkey>/page_images/contact_sheet.jpg` when available
- `papers/<bibkey>/math_pages/page-*.png` when formula parsing quality is poor or theory equations are missing
- `papers/<bibkey>/paper.pdf` when parsed text or visual evidence is incomplete
- `schemas/math_index.schema.json`
- `schemas/source_map.schema.json`
- `schemas/deep_read_report.schema.json`

## References To Load

- Read `references/paper-profile.md` first to choose the primary paper type and active lenses.
- Read `references/paper-type-contracts.md` before deciding which type-specific sections are required.
- Read `references/reading-plan.md` before writing `note_plan.json`.
- Read `references/source-map.md` before writing any claim, result, or visual card.
- Read `references/argument-anatomy.md` before filling the argument map.
- Read `references/numeric-results.md` before extracting metrics or comparisons.
- Read `references/visual-card.md` before adding figure/table evidence.
- Read `references/output-contract.md` before writing artifacts.

## Outputs

Write exactly these paper-local artifacts:

- `papers/<bibkey>/source_map.json`
- `papers/<bibkey>/note_plan.json`
- `papers/<bibkey>/deep_read.json`

`formula_vision.json` and `math_index.json` vision fallback status are generated by `battery_lit read <bibkey> --vision-formulas`. Do not hand-write those files unless the CLI itself is being tested.

`source_map.json` records the source blocks actually used by the reading report, including `E### external source block` entries for external availability evidence. It is not a full-paper bilingual reader and should not attempt to translate the entire PDF.
`note_plan.json` records the reading route: one primary paper type, multiple active lenses, must-cover points, key numbers, central claims, claim boundaries, and visual plan.
`deep_read.json` records quick-read takeaways, argument map, central claims, type-specific understanding sections, evaluation, numeric results, visual cards, availability, extraction notes, and Chinese translations under `translations.zh`.

## Reading Process

Use an evidence-harvest -> interpretation-draft -> schema-write -> self-review gate workflow. Do not use the schemas as the first writing outline, and do not start by filling every schema field from top to bottom.

1. Read metadata first so bibkey, title, authors, year, venue, DOI/arXiv, and PDF path stay consistent with the library.
2. Read `paper_index.json` and `math_index.json` before `parsed.md`. Use sections, paragraph IDs, parser-quality notes, and formula candidates to locate the few passages needed for the report; do not read the full paper blindly.
3. Inspect headings first, then abstract, introduction, method/theory, experiments/results, limitations, figures/tables, and appendix cues in chunks.
4. If `math_index.json` says `vision_fallback.needed` and the text candidates are insufficient, run `battery_lit read <bibkey> --vision-formulas` before writing the report bundle. This is the only allowed Codex image-input exception. Use the resulting `formula_vision.json` equations as formula evidence, and cite their image paths through `M###` source blocks in `source_map.json`. If the command records `blocked`, `exhausted`, or `completed_no_formula` in `vision_fallback.status`, explain why before relying on `extraction_notes.low_confidence_equations`.
5. Evidence-harvest: build `source_map.json` before final writing. Create stable block IDs for every source block used as evidence, such as `S001` for body text, `C001` for caption text, `F001` for figure evidence, `T001` for table evidence, `M001` for math/vision-transcribed formula evidence, and `E001` for external availability evidence. Body and caption blocks must include `section_id`, `paragraph_ids`, and `source_kind`. For theory-heavy papers, preserve cleaned equation/theorem/definition blocks as source evidence rather than reducing them to prose summaries.
6. Build `note_plan.json`. Choose one `primary_type` and any number of `active_lenses`; active lenses must include the primary type.
7. Interpretation-draft: draft the paper-specific interpretation from the source map and note plan before converting it into schema-shaped JSON. The draft must be understandable to an adjacent-domain reader who has not opened the PDF: name the actual method, mechanism, equations/variables, task, dataset, baseline, metric, constraint, limitation, or method family whenever the paper provides them. Every quick-read item, argument-map item, central claim, evaluation result, numeric result, and visual card must cite `source_refs`. For active `theory`, include problem formulation, key equations, theorem/principle chain, and engineering proof sketch. Do not skip key equations merely because parsed text is degraded unless `math_index.json` records that vision fallback was blocked or exhausted. For active `survey`, include taxonomy, method-family matrix, and timeline milestones when the paper provides them. A survey matrix row is allowed only when the paper evidence supports a concrete mechanism, strength, limitation, and best use case; do not add low-confidence filler rows saying that a family is merely mentioned or needs more reading. For active `dataset_benchmark`, use the `structured_v2` contract: separate corpus facts into `key_numbers`, reconstruct the ordered production workflow in `construction_steps`, and keep downstream model/solver metrics in `evaluation`.
8. Run the External Availability Search Protocol below before finalizing availability. For code, data, and model availability, do not rely only on the paper text.
9. Schema-write: build `deep_read.json` from the interpretation draft, source map, note plan, and availability search results. Also write `translations.zh` for all reader-facing conclusions and availability evidence/notes; do not translate paths, BibTeX keys, DOI/arXiv IDs, URLs, numbers, equations, or source IDs. Validation fails if required reader-facing Chinese translations are missing.
10. Run an explicit interpretation-quality pass before validation. Reader-facing English must explain the paper in your own words; do not wrap source blocks with phrases like "the paper frames its contribution around", "the motivating problem is", "the main evidence is", "concrete intervention or analysis route", "tasks, baselines, or benchmarks", "scoped support", "studies an optimal-control method or theory component", or "the key evidence is that". Do not paste long source paragraphs into quick-read, argument-map, central-claim, method, evaluation, availability, or type-section prose. Source-map blocks preserve quoted evidence; reading results interpret that evidence. Every quick-read item must name a concrete method, theorem, example, equation family, dataset, solver, benchmark, code artifact, or limitation from this paper.
11. Run an explicit Chinese coverage pass before validation. `translations.zh` must structurally mirror the reader-facing English fields that will appear in Markdown or HTML: summary, quick-read, argument map, central claims, method, active type sections, evaluation, visual cards, availability, and extraction notes. Do not copy English sentences into Chinese fields as a fallback. Do not write generic "躺平式" Chinese such as "结合英文证据/source_refs 理解", "以原文为准", repeated "该论文从某方向出发" placeholders, "这张卡片说明文献如何处理最优控制中的建模、求解或理论分析", or "文献给出一种围绕最优控制建模与求解的结构化说明". Short technical names may stay bilingual or English, but explanatory sentences must be Chinese and paper-specific. The validator rejects missing, copied-English, mostly-English, parser-residue, template-like, or lazy generic reader text.
12. Self-review gate: before validation, confirm that evidence has been harvested before interpretations, interpretations are paper-specific and concrete enough for a reader to understand the paper without the PDF, schema fields cite real `source_refs`, availability includes the required local and external checks, Chinese coverage mirrors reader-facing English, and no internal instructions leak into reader-facing prose. Do not write prompt text, reading-plan rationale, validator requirements, quality-audit wording, schema instructions, or workflow status into reader-facing results. Never mention "this reread", "the reread", "selected evidence", "evidence block", "reading bundle", "validation error", "本次重读", "所选证据", or "证据块" in user-facing English or Chinese results.
13. Use the visual evidence protocol:
   - Read `visual_index.md` if present.
   - Inspect `page_images/contact_sheet.jpg` first.
   - Open only the small set of page images needed for key figures, tables, algorithms, and appendix evidence.
   - If only a full-page image is available, use `crop_status: "full_page_approximate"` and say so in `extraction_notes.visual_crop_limitations`.
   - Verify that the card label, caption, page number, and image path all refer to the same visual evidence before writing the final card.
   - Set `placement_section` so the visual appears next to the section it supports.
14. Preserve uncertainty. Use `extraction_notes` for parser gaps, low-confidence equations, missing sections, approximate visual crops, vision fallback blockers, and external information.
15. Do not invent citations, implementation details, numbers, dataset names, code links, formulas, or claims that are not supported by source blocks.

## External Availability Search Protocol

Availability is a bounded evidence task, not a guess from paper memory. For code, data, and model availability, do not rely only on the paper text: after harvesting local paper evidence, run a limited external search for official availability signals.

- Start from URLs, DOI/arXiv pages, repository links, dataset links, model-card links, project pages, OpenReview/publisher supplement pages, and author-provided links already present in the paper or metadata.
- If those are absent or stale, run at most a few targeted lookups using the paper title plus `code`, `GitHub`, `dataset`, `data`, `model`, `Hugging Face`, `supplementary`, or the named benchmark/model artifact.
- Use only external pages you actually opened. Prefer official project, author, publisher, repository, dataset archive, model hub, or DOI/arXiv-linked pages over search-result snippets or third-party mirrors.
- For every external fact used in `availability.code`, `availability.data`, or `availability.models`, add an `E### external source block` to `source_map.json` with `source_kind: "external"`, `page: 0`, `section: "External availability"`, `section_id: "external_availability"`, `source_text` summarizing the opened source, and `notes` containing the page title, URL, access date, and search query or lookup path.
- Availability reader-facing `evidence` fields must interpret that external source for the reader. Do not copy the `E###.source_text` string or HTTP/search result verbatim; say whether code/data/models appear available, where, and what caveat matters.
- Cite the `E###` block in the relevant availability `source_refs`. If an availability conclusion uses both paper text and an external page, cite both the local block and the `E###` block.
- If external search is blocked, unavailable, or inconclusive, record that in `extraction_notes.external_info_used` and in the relevant availability `notes`; do not invent links or treat model memory as evidence.

Keep progress narration sparse. Report real blockers and the final verification summary, but do not narrate routine file reads, parser setup, validator retries, or tool-selection details unless they change the user-visible result.

If a copied topic skill conflicts with the project-root schemas or validator, the project-root schemas and validator are authoritative.

## Validation

After writing all artifacts, run:

```bash
battery_lit read <bibkey> --validate-report
battery_lit read <bibkey> --rebuild-note
battery_lit read <bibkey> --quality-audit
```

`read --rebuild-note` refreshes static HTML automatically. Run `quality-audit` after rebuild so it checks the current Markdown and HTML. Run `battery_lit html build` manually only after direct file edits, HTML repair work, or when automatic refresh was disabled with `BATTERY_LIT_AUTO_HTML=0`.

After any multi-paper reading job, run:

```bash
battery_lit tool audit-readings --json
```

This catches cross-paper template reuse that single-paper validation cannot see. If it reports repeated reader-facing text blocks, fix the affected papers before treating the reading job as complete.

If validation fails, fix `source_map.json` or `deep_read.json` rather than loosening the schema.
