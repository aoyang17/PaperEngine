# paper_reread

Use this skill when the user explicitly asks to reread a paper or replace stale/low-quality reading results. It is a thin control skill: it defines how to avoid old-artifact contamination, then routes the actual reading work through `skills/paper_deep_read/SKILL.md`.

Do not use this skill for a normal first read unless the user specifically asks to force a reread. For normal read requests, `skills/paper_deep_read/SKILL.md` is enough.

## Inputs

Required:

- one named `bibkey`, or a short explicit list of named `bibkey` values
- current topic root

Do not infer the target paper by scanning `papers/*`. If the user did not name the paper, ask for the bibkey or use `battery_lit library find --json --query TEXT` with the user's title/query.

## Core Rule

Existing reading artifacts are targets to replace, not evidence to reuse.

For the target `bibkey`, do not use these files as reading evidence:

- `papers/<bibkey>/source_map.json`
- `papers/<bibkey>/note_plan.json`
- `papers/<bibkey>/deep_read.json`
- `papers/<bibkey>/note.md`
- `papers/<bibkey>/note_zh.md`
- `papers/<bibkey>/reading_result.html`

You may only use them to confirm which files will be overwritten. If an old artifact conflicts with paper evidence, ignore the old artifact.

Use only:

- `papers/<bibkey>/metadata.yml`
- `papers/<bibkey>/paper.pdf`
- `papers/<bibkey>/parsed.md`
- `papers/<bibkey>/paper_index.json`
- `papers/<bibkey>/math_index.json`
- `papers/<bibkey>/formula_vision.json` when generated by the CLI
- `papers/<bibkey>/visual_index.md`
- selected `page_images/` or `math_pages/` files
- opened external availability sources
- project-root schemas and `skills/paper_deep_read/SKILL.md`

## Multi-Paper Workflow

If the user names more than one `bibkey`, asks to reread all library papers, or asks to regenerate/update library knowledge cards in bulk, do not loop over paper directories and do not write final `papers/<bibkey>/source_map.json`, `note_plan.json`, or `deep_read.json` directly.

Use the project-controlled per-paper read pool:

```bash
battery_lit read-many --bibkey <bibkey> [--bibkey <bibkey> ...] --force-reread --json
```

For all-library rereads, use:

```bash
battery_lit read-many --all-library --force-reread --json
```

`read-many` creates one independent job per paper. Each job owns exactly one reader session and one independent reviewer session. The reader writes staged artifacts under `.tmp/read_pool/<run_id>/<bibkey>/draft/`; the reviewer inspects those staged artifacts and paper evidence; the controller copies accepted artifacts into `papers/<bibkey>/` only after reviewer approval, `validate-report`, `rebuild-note`, `quality-audit`, and selected reduce audit pass.

Use the default project parallelism for normal user work: omit `--max-parallel` and let `read-many` use 5 paper jobs. For development probes, add `--max-parallel 3`:

```bash
battery_lit read-many --bibkey <bibkey> [--bibkey <bibkey> ...] --force-reread --max-parallel 3 --json
```

Use `--max-parallel N` above 5 only when the user explicitly asks for higher throughput. The hard cap is 20 paper jobs, and each paper job owns one reader session plus one reviewer session, so `--max-parallel N` may start up to 2N Codex sessions.

The reader may receive reviewer/CLI feedback and retry within the same reader session. Each paper job runs at most three reader-review cycles by default and exits early once all gates pass. If a failed paper needs more repair, rerun only the failed bibkeys with `--max-cycles N`; the project hard cap is 7. If `read-many` reports a failed bibkey, report the bibkey and concrete error; do not manually overwrite final artifacts. Do not use `--accept-last-on-max-cycles` unless the user explicitly asks to accept a still-limited last draft; even then, the controller may accept it only after schema validation, rebuild, and quality audit pass, and it must mark the JSON/HTML as accepted with limitations.

Never create or run a deterministic draft writer, helper script, parsed/index-only bulk generator, schema filler, or any other generic program that fabricates reading bundles across papers. The staging directory is for per-paper reading drafts only. Each draft must come from the `paper_deep_read` evidence-harvest -> interpretation-draft -> schema-write -> self-review workflow for that paper.

## Dataset-Only Refresh

When the user explicitly asks to update only the dataset section of an existing valid knowledge card, do not run a full reread. Use:

```bash
battery_lit read-many --bibkey <bibkey> --refresh-section dataset --json
```

This reuses existing parser artifacts and the normal persistent reader/reviewer cycle. The reader writes only a staged dataset patch; the controller preserves the summary, profile, argument, method, evaluation, other type sections, and note plan. The patch may replace only `dataset_benchmark_understanding`, its Chinese mirror, dataset visual cards, `availability.data`, and their source blocks.

Write the refreshed module as permanent reader-facing content. Do not mention rereading, updating, old results, patches, prompts, schemas, validators, reviewers, parsing workflow, or the current task. If the existing report is invalid, the dataset lens is inactive, or the requested change requires revising cross-cutting conclusions, stop and use the normal full reread workflow instead.

## Probe Sizing

Use the smallest realistic probe that matches the change being tested. Do not run a full five-paper probe merely because it is available.

- Documentation, skill wording, or test-only edits: run the relevant unit/contract tests first. Do not start a new live Codex reread probe unless the edit changes worker prompts, generated artifacts, validation behavior, or finalization behavior.
- Field-level renderer, translation, or validation edits: test one or two named papers that exercise the changed field.
- Prompt or quality-gate edits: test a mixed three-paper run covering at least two paper types, with `--max-parallel 3`.
- Reader/reviewer orchestration, retry, finalization, or repeated-text audit edits: test at least five papers, with `--max-parallel 3` in development unless the user explicitly asks for a throughput test.
- All-library or large-run edits: test at least ten papers across more than one paper type, then run a full-library audit. The second and third live validation rounds may be merged into one larger adversarial run when both target the same code path.
- If a multi-paper probe shows individual readers passing but reduce audit failing, do not add a regex patch. Tighten the reader/reviewer prompt or repair routing, then rerun the same paper set before scaling again.

If a probe fails, first decide whether the failure is a harness/process issue or a paper-content issue. Avoid adding phrase lists or one-off validators to satisfy a single failure; prefer tightening the LLM reading workflow, evidence pack, worker bounds, or repair path.

After a scoped probe passes, stop and report the evidence. Do not scale to a larger live run just to gain confidence unless the change touches cross-paper state, final library audit, or user-facing bulk behavior.

## Single-Paper Workflow

For one named paper:

1. Run basic checks from the topic root:

```bash
battery_lit policy check --json
battery_lit status --json
battery_lit library find --json --query <bibkey>
```

2. Rebuild parser artifacts before writing the new reading bundle:

```bash
battery_lit read <bibkey> --parse-only
```

3. Inspect `papers/<bibkey>/math_index.json`. If formula parsing is poor or `vision_fallback.needed` is true, run:

```bash
battery_lit read <bibkey> --vision-formulas
```

This is the only nested/model-backed exception allowed by the reading workflow.

4. Load and follow `skills/paper_deep_read/SKILL.md`. Read its referenced files as needed. Reconstruct the reading from evidence, not from the previous `deep_read.json`.

5. Overwrite only these hand-written paper-local artifacts:

- `papers/<bibkey>/source_map.json`
- `papers/<bibkey>/note_plan.json`
- `papers/<bibkey>/deep_read.json`

Do not hand-edit generated `note.md`, `note_zh.md`, `reading_result.html`, `parsed.md`, `paper_index.json`, page images, or formula fallback files.

6. Validate and rebuild:

```bash
battery_lit read <bibkey> --validate-report
battery_lit read <bibkey> --rebuild-note
battery_lit read <bibkey> --quality-audit
```

7. If more than one paper was reread, or after `read-many` completes, run:

```bash
battery_lit tool audit-readings --json
```

Fix repeated/template reader-facing text before reporting completion.

## Reader/Reviewer Agent Use

For multi-paper rereads, reader/reviewer sessions inside `battery_lit read-many` are the default path, not an optional optimization. They are useful for speed and quality only when each paper owns its own reader context and its own independent reviewer context. The main Codex session must not write multi-paper draft contents; it invokes `read-many`, watches results, and reports blockers.

Per-paper roles:

- Reader session: read only one named paper's allowed evidence, generate that paper's staged `source_map.json`, `note_plan.json`, `deep_read.json`, and write `reader.json` provenance. Do not write final `papers/<bibkey>/` artifacts.
- Reviewer session: independently inspect the staged artifacts and paper evidence for prompt leakage, old-artifact reuse, generic wording, weak Chinese, missing formula fallback, visual mismatch, or unsupported claims. Write only `review.json`; do not rewrite artifacts.

Avoid these patterns:

- Do not let the main session or several subagents write final `deep_read.json` files directly.
- Do not split one paper into several writers and merge their JSON by hand.
- Do not let subagents read sibling topic folders or unrelated paper directories.
- Do not let subagents use old notes or old `deep_read.json` as a source.

If reader outputs conflict with validation or reviewer findings, `read-many` feeds that paper-specific feedback back to the same reader session. Starting a fresh repair session is a fallback only after the existing reader session is blocked or exhausted.

## User-Facing Completion Summary

Report only:

- which bibkeys were reread
- which artifacts were overwritten
- validation, rebuild-note, quality-audit, selected reduce-audit, and final library-audit results when applicable
- any real blocker such as missing PDF, formula fallback blocked, external availability search blocked, or persistent quality-audit failure

Do not narrate routine instruction loading, sandbox retries, schema repair attempts, or validator wording. Do not mention "this reread" inside reader-facing paper results.
